# Tanzania fiscalization parity matrix

This matrix compares the uploaded `vpos-fiscal-tz` package against the FTC-native Tanzania fiscalization implementation in `vpos-ftc-app`. The package remains a reference implementation only. Do not add it as a runtime dependency and do not copy its certificate assets into FTC.

## Scope and boundary

- Reference package inspected: `vpos-fiscal-tz`.
- Application under change: `vpos-ftc-app`.
- Policy: FTC ports, replaces, or deliberately omits behavior in its own modules. The reference package is not modified.
- Production configuration target: database settings and secure artifacts. `.env` values are developer-only fallbacks.

## Intentional differences

1. FTC does not add `@gilbarcoafs/vpos-fiscal-tz` as a runtime dependency. The reference package informs behavior, but the production code remains FTC-native.
2. File-backed queues and JSON artifact files in `vpos-fiscal-tz` are replaced by FTC database tables, station-scoped settings, station KV wrappers, audit events, and secure artifact storage.
3. `.env` support is limited to developer fallback. Production values must be loaded from station settings, station KV, database rows, or secure artifacts.
4. Certificate, private key, and passphrase files from the reference package are not copied into FTC source or release bundles. FTC must use secure artifact storage and explicit rotation procedures.
5. Printer/template output from the reference package is not assumed to be in first-release scope until physical fiscal printer or PDF receipt requirements are confirmed.
6. EWURA failure policy is explicit and configurable. FTC defaults to non-blocking `async_retry` after TRA success, while a station can opt into `block_transaction` if operations requires EWURA confirmation before a transaction is treated as complete.
7. FTC may store more audit and retry metadata than the reference package because FTC must support dashboard visibility, cloud/proxy routing, and field-support diagnostics.

## Next acceptance checks

- Validate TRA token/authentication behavior against real endpoint credentials and confirm `ackcode=7` success semantics in the target environment.
- Validate TRA registration behavior against real endpoint credentials and confirm `ACKCODE=0` success response handling.
- Validate receipt verification QR URLs against TRA production and virtual verification portals.
- Run the new TRA/EWURA parity validators against field-approved payload fixtures from the first commissioned site.
- Validate z-report submission and day-close totals with live TRA credentials before claiming endpoint validation.
- Validate legacy `vpos-fiscal-tz` queue/artifact imports against a copied site backup folder.
- Validate EWURA retry/reconciliation behavior against live EFPP errors, duplicate posts, and recovery after endpoint downtime.
- Rehearse both Tanzania route cutover directions and confirm the API blocks unsafe switches while queues/config are incomplete.
- Route the FTC text output renderers to the approved physical printer, PDF receipt, or support-preview channel once site scope is confirmed.
- Use the FTC simulator fetch transport for offline TRA/EWURA field-validation rehearsals before switching to live endpoint credentials.
- Add secure-artifact validation diagnostics UI for missing, PFX-only, or expired Tanzania certificates.
- Run live endpoint validation with real TRA/EWURA credentials after commissioning approval.
