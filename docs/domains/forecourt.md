# Forecourt and DOMS/JPL

**Type:** authoritative

The forecourt module owns DOMS/JPL connection lifecycle, command execution, pump and tank state, transaction recovery, pricing, reconciliation, alarm handling, and commissioning evidence.

## Ownership

- Application workflows: `src/modules/forecourt/application/`
- Protocol and runtime infrastructure: `src/modules/forecourt/infrastructure/jpl/`
- Integration gateway: `src/modules/forecourt/infrastructure/core/`
- UI and administrative controls: `components/admin/forecourt/` and related routes

Compatibility exports under `src/shared/forecourt/` should be reduced over time. New protocol behavior belongs in the forecourt module.

## Safety properties

- Commands must retain correlation and timeout diagnostics.
- Reconnect and retry behavior must not duplicate dispense or maintenance actions.
- Transaction recovery must be idempotent and concurrency-safe.
- DOMS transaction buffer replay must be deferred until the station has a complete pump/nozzle/product mapping. A buffer entry may only be cleared after the corresponding transaction has been durably captured with that configured mapping.
- Durable capture for DOMS replay includes successful persistence of the transaction-to-checkpoint/replay ownership correlation. A transaction row that exists or has already fiscalized does not by itself authorize a clear if the lifecycle linkage update failed; replay remains fail-closed until the current buffer entry is correlated and marked `captured`.
- Supervised DOMS transaction clearing follows DPP 806449/04 ETS semantics: `clear_FpSupTrans_req` uses SUBC `04H` with the exact `FpId`, `PosId`, `TransSeqNo`, `Vol_e`, and `Money_e` from the collected transaction. The generic vendor `@gilbarcoafs/doms-pos-jpl` schema permits `PaymentParameters` to be absent, but the deployed PSS/JTM rejects SUBC `04H` before DPP conversion when that property is missing. VPOS therefore always sends `PaymentParameters: {}` for supervised ETS clears at this integration boundary. The payment group remains present because the deployed JTM requires it, while `ReferenceNo` is intentionally omitted so VPOS does not encode a zero-length ARRAY[BYTE] or manufacture payment-reference bytes for this clear path. A successful clear response is not treated as final proof of mutation; VPOS re-reads the authoritative transaction-buffer status and marks the local checkpoint `cleared` only after that exact `TransSeqNo` is absent.
- A supervised clear rejected as `0031H/04H`, `RejectCode 02H`, `RejectInfo 09H` (`Wrong rx_size`) is treated as a deterministic protocol/configuration failure for the current JPL session. The vendor client's `RejectError` retains the original PSS reject envelope under `details.raw`; VPOS classifies quarantine and protocol health from that structure rather than relying on the flattened error message. It quarantines that exact `(station, supervised, FpId, TransSeqNo)` from automatic clear retries so the transaction remains buffered and recoverable without creating a retry storm. The quarantine is reset on a new successful JPL session, after confirmed PSS configuration refresh, or by an explicitly confirmed live transaction-recovery run. It never marks the controller entry cleared.
- JPL adapter startup is process-single-flight. Concurrent callers share one startup promise so a single FTC process cannot create two simultaneous DOMS/JPL clients, listener sets, or startup reconciliation sweeps for the same runtime instance.
- JPL reconnects are serialized behind physical client teardown. The active DOMS socket is disconnected before the POS-session lease is released or a replacement client is created, and process shutdown always closes the currently active client rather than a client captured during the first startup. The POS-session lease heartbeat is independent of fallback polling and remains active for the lifetime of the physical session.
- Normal pump-status fallback retains the controller-wide `FpStatus_req` with `FpId = 00`; it must not be expanded into one request per configured pump. Transaction-buffer status is consumed directly from the JPL client's `unsolicited` stream and routed through the same bounded persistence/event-processing path as other forecourt events. This deliberately avoids vendor watcher dedupe/flag assumptions because deployed DOMS versions can omit the `solicited` property on valid unsolicited buffer snapshots and can change buffer contents while the latest stored sequence remains unchanged. Solicited startup/fallback reconciliation responses remain owned by the request initiator, preventing duplicate replay. Startup reconciliation is paced between buffer requests, and routine fallback starts only after that reconciliation completes. The default fallback cadence is 60 seconds, checks only buffer modes stale for at least 180 seconds, and reconciles at most eight pump/mode candidates per cycle in round-robin order. A successful DOMS transaction-buffer SUBC is remembered for the active session so unsupported variants are not retried for every pump.
- JPL persistence and normal inbound event processing are process-wide bounded queues. Durable transaction-bearing events remain FIFO and are never discarded or coalesced. Normal event processing defaults to one concurrent handler because deployed controllers may omit response correlation IDs; this prevents overlapping replay request/response flows from relying on FIFO correlation fallback. All application-issued solicited JPL requests also pass through one shared request gate: correlated controllers may use bounded concurrency, but the gate automatically collapses to strict single-flight whenever the vendor client reports correlation as unavailable or unknown. Replaceable pump-state materialization is separately bounded and pending `FpStatus` snapshots may coalesce to their newest value. Fallback polling yields when PostgreSQL, JPL persistence, event processing, or state materialization is backlogged.
- Routine `/admin/forecourt` diagnostics use a bounded adapter-state projection and expensive commissioning, reconciliation, maintenance, diagnostics, and support panels load only when explicitly requested. The full in-process DOMS/JPL snapshot remains available to an explicitly generated support bundle.
- The support bundle performs a read-only inspection of the authoritative imported `pss.xml.raw` source for `MlenReferenceNo` and related reference-length properties. It exposes only discovered property/value pairs and the source checksum; it does not include the raw XML or modify PSS configuration.
- `TransSeqNo` is a rolling DEC4 controller sequence and is reused after rollover and after a DOMS Master Reset. VPOS must therefore distinguish physical transaction incarnations with controller finish/reset evidence rather than treating `(station, mode, FpId, TransSeqNo)` as a lifetime-unique sale. Every locked transaction is normally re-read from DOMS before capture/clear; cached clear payloads and process-local seen keys must not suppress a currently present buffer entry. The sole short-lived exception is a stale post-clear buffer snapshot that still carries this POS lock immediately after VPOS has verified that the same sequence is absent: that snapshot is ignored for a bounded grace period, and a later DOMS `Trans not found` reject for an already-cleared checkpoint is treated as confirmation of absence rather than a new replay failure. This does not make a DEC4 replay key permanently terminal.
- `FpSupTrans_resp` / `FpUnSupTrans_resp` transaction parameters requested through `TransParId` are returned under `TransPars`. Capture must preserve `FcGradeId` and `FpGradeOptionNo`; exact grade-option/nozzle evidence takes precedence, and a grade shared by multiple nozzles is not guessed.
- Transaction-buffer monitoring prefers ETS status SUBC `03H` with `01H`/`00H` compatibility fallbacks, matching `UNSO_TRBUFSTA_3`. DPP RejectCode `03H` is treated as a request that cannot currently be processed, not as permanent loss of transaction-buffer access; later unsolicited events and fallback polls remain eligible to retry, and replay capability state is reset for every successful JPL session.
- Importing PSS XML invalidates the in-process DOMS mapping cache and immediately attempts buffer reconciliation when the JPL client is connected, so transactions that were present before commissioning can be recovered without restarting the app.
- PSS XML topology identity preserves `FuellingPoint ID` as the primary DOMS pump identity and uses `(PSSPortNo, PhysicalAddress, DeviceSubAddress)` as the transport-address fallback. `DeviceSubAddress` is not globally unique: valid PSS configurations may repeat it on the same PSS port under different physical addresses. Grade-option identity is also distinct from physical `NozzleId`; imports store both, preserve every `<Part TankID=...>` link for manifolded/multi-tank nozzles, and treat a subsequent PSS import as authoritative for DOMS-managed pumps/nozzles. Removed nozzle mappings are retired rather than deleted so historical transaction foreign keys remain valid.
- The ATG polling worker is station-configurable and disabled by default. When enabled it invokes the existing `GET_ALL_TG_DATA` JPL command at the configured interval (10 minutes by default), updates the current `tanks.live_volume_*` fields, and upserts exactly one local `tank_atg_snapshots` row per configured tank. DOMS fixed-point TgData values are converted to physical units before persistence and publication (`FC_TANK_VOL` /100, `FC_TANK_LEVEL` /10, `FC_TANK_MASS` /10, temperature /10, and pressure /10); density remains the protocol integer value. `TankDataLastUpdateDateAndTime` is interpreted as controller-local wall time in the station's configured IANA timezone before it is stored as `timestamptz`. The latest snapshot also retains the TgData online/inventory-ready/alarm/error quality flags. The normal collection path does not issue a second `TgStatus_req` because these quality flags already accompany each `TgData_resp`; the broader status snapshot is opt-in for diagnostics. The snapshot contains station-owned product/tank names and capacity plus temperature, temperature-compensated volume, observed volume, DOMS `TankId`, and the remaining normalized TgData fields. A positive configured tank capacity wins; if none exists, snapshot publication falls back to DOMS `TankShellCapacity`, then `TankMaxSafeFillCapacity`, without overwriting station tank configuration. Every poll replaces the prior current-state snapshot and also writes a normalized, payload-free row to `tank_atg_capture_evidence`; that evidence is pruned inline after 30 days and exists only so a delayed transaction can select a complete capture from at or before its sale timestamp. Cloud services continue to own long-term ATG history. Raw JPL payloads are not retained; a payload hash is stored for traceability. After the database transaction commits, runtime orchestration publishes the complete just-captured snapshot set for Tanzania stations to the Tanzania proxy tank-inventory contract. Non-Tanzania stations skip that publication. A partial current capture is not uploaded as a complete station snapshot.
- The `/settings/tanks` **Sync DOMS volumes** action uses the same `GET_ALL_TG_DATA` capture/persistence path as the ATG worker, including DOMS fixed-point scaling, station-timezone conversion, `TgId -> tanks.doms_tank_id` matching, current `tanks.live_volume_*` updates, and latest-snapshot replacement. The response reports the number of tank rows actually persisted and separately reports requested gauge count/controller errors so partial reads are visible instead of being reported as zero. The tank settings table and edit sheet surface the latest read-only ATG observed/TC volumes, product level, water, temperature, quality state, and controller timestamp; configured capacity and manual-volume inputs remain operator-owned and are not overwritten by sync. The `/settings/tanks` manual sync itself does not publish Tanzania tank inventory to the cloud; scheduled runtime publication remains its cloud handoff path.
- The `/tanks` **Refresh Tank Gauge Data** action is also a mutating ATG refresh: it uses the same persisted `GET_ALL_TG_DATA` capture, then maps each successfully persisted `TgId` to the corresponding 1-based tank slot and updates only that slot's `tankLevels` value used by the `/tanks` virtual-tank totals. It does not create new tank slots or change grade/active assignments. The response reuses the same controller readings for the live gauge panel, avoiding a second DOMS poll. After that local refresh succeeds, `/tanks` explicitly requests publication of the exact just-captured snapshot set through the Tanzania tank-inventory publisher. Tanzania stations therefore send the fresh complete capture to `vpos-proxy` immediately; non-Tanzania stations are skipped by the country boundary. A publication rejection is surfaced as an error rather than reporting the manual operation as fully successful.
- The `/tank-levels` operational level cards treat a persisted `tanks.live_volume_litres` ATG reading as the authoritative current physical level whenever one is available. Stock-count/manual baselines and delivery/deduction movements remain visible as accounting context and are used as the fallback estimate only when there is no live ATG volume; an older accounting baseline must not mask a newer gauge reading. The page surfaces the ATG source and controller-derived update time when live data is driving the current level.
- Tanzania transaction reporting does not mutate these physical ATG values. A separate persisted regulatory projection may aggregate same-grade tanks in a configured tank group and deduct sale litres between ATG captures, while the next `GET_ALL_TG_DATA` result remains the physical source of truth. Tanzania daily totals continue to enumerate each physical tank separately from the latest complete ATG capture.
- Maintenance writes require explicit authorization and operational gates.
- Live field validation is required before declaring deployment readiness.

Core implementation work recorded in the historical DOMS checklist is complete. External validation, approval, and deferred scope are classified in [`../../DOMS_REMAINING_WORK.json`](../../DOMS_REMAINING_WORK.json).
